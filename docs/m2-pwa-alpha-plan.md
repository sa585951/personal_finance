# M2 PWA Alpha Plan

## 目標

M2 要驗證的不是功能是否存在，而是非開發者能否在手機上自行完成 Nomica 的核心流程，並理解日常帳務與旅行分帳的差異。

本輪招募 5 至 10 位測試者，觀察以下問題：

- 第一次使用時，是否能完成登入、建立帳戶與記錄第一筆收支。
- 平常是否願意使用「記一筆」或 LINE 快速記帳。
- 旅行建立者是否能完成邀請、共同支出、分攤與群組結算。
- 受邀成員是否理解自己的分攤、待收／待付與個人月報偏好。
- 使用者卡住時，問題來自功能錯誤、操作入口、名詞，還是缺少說明。

M2 是操作可用性 Alpha，不是財務正確性 Beta、留存驗證或市場驗證。

## 測試邊界

- `Payment != Expense`：付款人先付款，不代表整筆都是付款人的個人支出。
- `Settlement != Income / Expense`：旅行結算不是新的收入或支出。
- `Transfer != Income / Expense`：帳戶互轉不應進入收支月報。
- 目前旅行「確認結算」只更新群組分帳狀態，不會自動扣除或增加任何成員的私人帳戶餘額。
- PWA Alpha 驗證 Web 手機版操作；iOS 原生 App、離線同步、推播與正式 Apple Login 不在本輪範圍。

測試中若使用者把群組結算理解成銀行或帳戶已實際付款，視為阻塞級語意問題，即使計算結果正確也不能忽略。

## 測試者組成

建議分成三種角色，總數 5 至 10 人：

| 角色 | 建議人數 | 主要任務 |
| --- | ---: | --- |
| 日常使用者 | 2 至 4 | 登入、帳戶、第一筆收支、再次記帳、查紀錄 |
| 旅行建立者 | 1 至 2 | 建立旅行、邀請、共同支出、分攤與結算 |
| 受邀成員 | 2 至 4 | 接受邀請、查看自己的成本、設定月報偏好、理解待收／待付 |

同一人可以同時扮演日常使用者與旅行成員，但至少要有一組兩人以上的真實邀請流程。

## 測試前準備

由測試主持人確認：

1. Vercel、Render 與 Supabase 使用目前相容的部署版本，migration 已完成。
2. Production 的 `DEV_AUTH_BYPASS=false`，前後端 URL 與 LINE callback 正確。
3. 使用全新或可辨識的測試旅行，避免誤改正式資料。
4. 測試者知道 Nomica 不連接銀行、信用卡或券商，帳戶與餘額都由本人維護。
5. 告知測試者不要在回饋中貼出 token、完整帳戶名稱、精確餘額或其他人的個人資料。

## 測試流程

### Session A：第一次使用，約 10 分鐘

除非測試者完全無法繼續，主持人不要先教操作。

1. 從 LINE 或正式 Web 網址登入 Nomica。
2. 建立一個會追蹤餘額的現金或銀行帳戶。
3. 從首頁或紀錄頁找到「記一筆」。
4. 記錄一筆支出；可自由選擇 AI 或手動輸入。
5. 到紀錄頁找回剛才的交易。
6. 回到首頁，說出目前看到的本月狀態與一則 Insight。

記錄：每一步是否自行完成、卡住位置、錯誤訊息、是否需要主持人提示。

### Session B：日常回訪，隔 1 至 3 天

1. 再次開啟 Nomica，確認登入狀態與資料仍存在。
2. 新增一筆收入或支出。
3. 編輯或刪除一筆自己建立的交易。
4. 在紀錄頁查找最近資料，並嘗試依月份查找。
5. 開啟分析頁，說明自己認為圖表或摘要在回答什麼問題。

記錄：測試者是否記得入口、是否重複送出、是否理解紀錄與分析頁分工。

### Session C：旅行協作，約 20 分鐘

由一位旅行建立者與至少一位受邀成員共同完成。

1. 建立者新增旅行並送出邀請。
2. 受邀成員完成登入與加入。
3. 建立者新增一筆自己付款的共同支出並平均分攤。
4. 另一位成員新增或查看一筆他人付款的共同支出。
5. 雙方分別說明「整團花費」、「我的分攤」與「待收／待付」。
6. 各自選擇是否將這趟旅行納入自己的月報。
7. 查看並確認一筆群組結算，再說明帳戶餘額是否有被系統改動。

預期：每位成員只控制自己的月報偏好；月報只納入該成員的 split share；群組結算不異動私人帳戶。

## 成功門檻

M2 可收尾需同時符合：

- 至少 5 位非開發者完成 Session A。
- 至少 3 位測試者在沒有再次教學下完成 Session B 的新增流程。
- 至少 1 組兩人以上完成邀請、共同支出、分攤與結算流程。
- 登入、建立第一帳戶、建立第一交易三項流程成功率各達 80%。
- 沒有造成重複扣款、錯誤帳戶餘額或資料越權的 Sev 0／Sev 1 問題。
- 測試者不會普遍把群組結算誤認為私人帳戶已付款。
- 高頻阻塞問題已有修正、清楚 workaround，或明確延後理由。

回訪與市場需求只記錄訊號，不作為 M2 唯一通過條件。

## 問題分級

| 等級 | 定義 | 處理方式 |
| --- | --- | --- |
| Sev 0 | 資料外洩、越權、不可逆資料損壞或錯誤扣款 | 立即停止測試與部署擴散 |
| Sev 1 | 核心流程無法完成、重複交易、錯誤財務語意 | 先修復並回歸，再繼續 Alpha |
| Sev 2 | 可繞過但多人反覆卡住、名詞或入口明顯誤導 | M2 優先修補 |
| Sev 3 | 視覺、文案或低頻便利性問題 | 記錄到後續維護清單 |

M2 只接受 Sev 0 至 Sev 2 的必要修補，不因單一建議立即擴充新模組。

1. 哪一步最不確定下一個動作？
2. 哪個名詞最難理解？
3. 你會在什麼情境再次打開 Nomica？
4. LINE 與 Web 各自適合做什麼？

## 量測與隱私

- 第一輪使用主持人觀察與匿名代號表，不接第三方 analytics SDK。
- 不收集自然語言輸入原文、交易名稱、帳戶名稱、旅行名稱、精確金額、餘額、Email、LINE id、token 或 session id。
- 若後續需要自動事件，必須沿用 `docs/product-event-taxonomy.md`，並先決定 consent、provider 與 production privacy 策略。
- Analytics 或回饋紀錄失敗不得影響任何財務寫入。

## M2 收尾輸出

測試完成後產出：

1. 每個核心流程的完成率與提示次數。
2. Sev 0 至 Sev 3 問題清單及處理狀態。
3. LINE、Web 與 PWA 的入口分工結論。
4. 是否進入 M3 Ledger Correctness 的 go／no-go 決策。
5. 不阻塞 M2、但值得排入 M4 或後續維護的需求清單。

`docs/phase5-simulation-test-script.md` 繼續作為開發者深度回歸腳本，不取代本文件的非開發者 Alpha 流程。
